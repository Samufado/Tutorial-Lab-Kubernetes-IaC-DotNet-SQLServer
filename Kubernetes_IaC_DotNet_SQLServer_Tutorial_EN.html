Overview

Lab architecture

PowerShell reaches the API through localhost:8080. The API Service forwards port 80 to port 8080 in the Pod. The API connects to SQL Server through sqlserver:1433. A StatefulSet mounts a persistent volume.

A Job applies the EF Core migrations before you deploy the API Pods.

Use Windows x64 (Intel or AMD), Git, the .NET 10 SDK, and Docker Desktop with Linux containers or Rancher Desktop with Moby. Enable local Kubernetes. As a practical baseline, allow about 6 GB of RAM and four CPUs for the Linux environment on a 16 GB host.

The lab uses SQL Server Developer, a dedicated password, and a local unauthenticated API.

API and EF Core

How the project is organized

Models/Produto.cs defines the entity and HTTP input. Data/AppDbContext.cs maps the model to SQL Server. Program.cs configures the app and health endpoints. ProdutosEndpoints.cs defines the catalog routes. Migrator.cs applies migrations and exits.

The Dockerfile defines how to build the image. The k8s manifests declare the desired cluster state. Kubernetes reconciles the actual state with those declarations.

Product entity and request data

EF Core treats Id as the key by convention. Nome has an 80-character limit. ProdutoEntrada represents the JSON supplied on create and update.

SQL Server stores the products. Kubernetes can replace the API Pod while keeping the stored records.

API and EF Core

DbContext and mapping

DbSet<Produto> exposes a queryable collection. HasPrecision(18, 2) sets the SQL Server precision and scale for prices.

The API registers DbContext as scoped, giving each request its own context. Keep it separate across concurrent requests.

C#CatalogoApi/Data/AppDbContext.cs
using CatalogoApi.Models;
using Microsoft.EntityFrameworkCore;

namespace CatalogoApi.Data;

public class AppDbContext(DbContextOptions<AppDbContext> options)
    : DbContext(options)
{
    public DbSet<Produto> Produtos => Set<Produto>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Produto>()
            .Property(p => p.Preco).HasPrecision(18, 2);
    }
}
API and EF Core

Generate migrations without a local database

The EF CLI uses the design-time factory to inspect the model. Generating the migration requires no SQL Server instance on Windows.

At runtime, the Pods get their server settings and password through configuration and a Secret.

C#CatalogoApi/Data/AppDbContextFactory.cs
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Design;

namespace CatalogoApi.Data;

// Used by the migration generation command.
public class AppDbContextFactory : IDesignTimeDbContextFactory<AppDbContext>
{
    public AppDbContext CreateDbContext(string[] args)
    {
        var options = new DbContextOptionsBuilder<AppDbContext>()
            .UseSqlServer("Server=localhost;Database=Catalogo;" +
                "Integrated Security=true;TrustServerCertificate=true;")
            .Options;
        return new AppDbContext(options);
    }
}
API and EF Core

API connection settings

.NET maps Db__Server to Db:Server. The connection string builder handles password characters as values.

TrustServerCertificate=true simplifies the local connection. Validate the certificate in production. EnableRetryOnFailure retries transient failures.

C#CatalogoApi/Program.cs
using CatalogoApi;
using CatalogoApi.Data;
using Microsoft.Data.SqlClient;
using Microsoft.EntityFrameworkCore;

var migrateOnly = args.Contains("--migrate");
var builder = WebApplication.CreateBuilder(
    args.Where(a => a != "--migrate").ToArray());
var config = builder.Configuration;
var connection = new SqlConnectionStringBuilder
{
    DataSource = config["Db:Server"] ?? "sqlserver,1433",
    InitialCatalog = config["Db:Name"] ?? "Catalogo",
    UserID = config["Db:User"] ?? "sa",
    Password = config["Db:Password"]
        ?? throw new InvalidOperationException("Configure Db__Password."),
    Encrypt = true,
    TrustServerCertificate = true, // For the local training cluster only.
    ConnectTimeout = 5
}.ConnectionString;

builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connection, sql => sql.EnableRetryOnFailure(3)));
var app = builder.Build();
API and EF Core

Catalog routes

GET /produtos lists products. GET /produtos/{id} returns a product or 404. POST /produtos validates input, saves it, and returns 201 with the product. PUT /produtos/{id} updates its name and price. DELETE /produtos/{id} removes it.

Download the full endpoint file to see the remaining routes. Changes are saved with SaveChangesAsync.

C#CatalogoApi/ProdutosEndpoints.cs
        app.MapGet("/produtos", async (AppDbContext db) =>
            await db.Produtos.AsNoTracking().OrderBy(p => p.Id).ToListAsync());

        app.MapGet("/produtos/{id:int}", async (int id, AppDbContext db) =>
        {
            var produto = await db.Produtos.FindAsync(id);
            return produto is null ? Results.NotFound() : Results.Ok(produto);
        });

        app.MapPost("/produtos", async (ProdutoEntrada entrada, AppDbContext db) =>
        {
            if (Invalido(entrada))
                return Results.BadRequest("Informe nome (1 a 80 caracteres) e preco valido.");
            var produto = new Produto { Nome = entrada.Nome.Trim(), Preco = entrada.Preco };
            db.Produtos.Add(produto);
            await db.SaveChangesAsync();
            return Results.Created($"/produtos/{produto.Id}", produto);
API and EF Core

Liveness and readiness

/health/live checks the API process independently of the database. /health/ready checks whether the API can reach SQL Server. A database outage can remove the API from normal Service traffic while its process stays alive.

The readiness endpoint checks connectivity as defined for this exercise.

C#CatalogoApi/Program.cs
});
app.MapGet("/health/live", () => Results.Ok(new { status = "vivo" }));
app.MapGet("/health/ready", async (AppDbContext db, CancellationToken token) =>
{
    using var timeout = CancellationTokenSource.CreateLinkedTokenSource(token);
    timeout.CancelAfter(TimeSpan.FromSeconds(2));
    try
    {
        return await db.Database.CanConnectAsync(timeout.Token)
            ? Results.Ok(new { status = "pronto" })
            : Results.StatusCode(503);
    }
    catch
    {
        return Results.StatusCode(503);
    }
});
app.MapProdutos();
app.Run();
API and EF Core

Migration mode

The --migrate argument applies migrations and exits. The Job succeeds when the process exits with code zero. Bounded retries allow time for the database to start. Check the logs if the failure persists.

C#CatalogoApi/Program.cs
if (migrateOnly)
{
    await Migrator.RunAsync(app.Services);
    return;
}
C#CatalogoApi/Migrator.cs
using CatalogoApi.Data;
using Microsoft.EntityFrameworkCore;

namespace CatalogoApi;

public static class Migrator
{
    public static async Task RunAsync(IServiceProvider services)
    {
        for (var tentativa = 1; tentativa <= 24; tentativa++)
        {
            await using var scope = services.CreateAsyncScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            try
            {
                await db.Database.MigrateAsync();
                Console.WriteLine("Migrations aplicadas.");
                return;
            }
            catch (Exception) when (tentativa < 24)
            {
                Console.WriteLine($"Banco ainda indisponivel: tentativa {tentativa}/24.");
                await Task.Delay(TimeSpan.FromSeconds(5));
            }
        }
    }
}

Dockerfile build and runtime stages

The build stage uses the .NET SDK image to restore dependencies and publish the project. --locked-mode uses the resolved dependencies.

The final image contains the ASP.NET runtime and published files. USER $APP_UID runs the application as the unprivileged user in the .NET Linux image.

DockerfileCatalogoApi/Dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY ["CatalogoApi/CatalogoApi.csproj", "CatalogoApi/"]
COPY ["CatalogoApi/packages.lock.json", "CatalogoApi/"]
RUN dotnet restore "CatalogoApi/CatalogoApi.csproj" --locked-mode
COPY CatalogoApi/ CatalogoApi/
RUN dotnet publish "CatalogoApi/CatalogoApi.csproj" -c Release -o /out --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:10.0
WORKDIR /app
ENV ASPNETCORE_HTTP_PORTS=8080
COPY --from=build /out .
USER $APP_UID
EXPOSE 8080
ENTRYPOINT ["dotnet", "CatalogoApi.dll"]

Make the image available to the node

With Docker Desktop, check the provisioner under Kubernetes. Kubeadm is the main path. If a cluster exists, check Edit cluster. The docker-desktop context can refer to either provisioner.

Kubeadm or Rancher Desktop with Moby: build in the local engine and proceed to slide 22. Docker Desktop with kind: run the import block below after the build, from LabIaCK8s.

The script exports the Linux/AMD64 image and imports it into the local nodes. IfNotPresent lets Kubernetes use an image already on the node. The script requires Docker support for docker image save --platform. For ErrImagePull, inspect Pod events.

PowerShellscripts/Importar-Imagem-Kind.ps1
# Optional: only for Docker Desktop clusters using kind.
# Run from the LabIaCK8s directory after docker build.
$ErrorActionPreference = "Stop"
if ((kubectl config current-context) -ne "docker-desktop") {
    throw "Selecione o contexto docker-desktop antes de continuar."
}
$nodes = (kubectl get nodes -o json | ConvertFrom-Json).items.metadata.name
$containers = @(docker ps --format '{{.Names}}')
$targets = @($nodes | Where-Object { $containers -contains $_ })
if ($targets.Count -eq 0) {
    throw "Nao encontrei nos kind como conteineres. Este passo e apenas para kind."
}
docker image save --platform linux/amd64 --output tutorialk8s-api.tar tutorialk8s-catalogo-api:1.0
if ($LASTEXITCODE -ne 0) { throw "Falha ao exportar a imagem." }
foreach ($node in $targets) {
    docker cp .\tutorialk8s-api.tar "${node}:/tmp/tutorialk8s-api.tar"
    if ($LASTEXITCODE -ne 0) { throw "Falha na copia para $node." }
    docker exec $node ctr --namespace k8s.io images import --all-platforms /tmp/tutorialk8s-api.tar
    if ($LASTEXITCODE -ne 0) { throw "Falha na importacao para $node." }
    docker exec $node rm /tmp/tutorialk8s-api.tar
}
Remove-Item .\tutorialk8s-api.tar

SQL Server memory and storage

The lab uses Developer edition with no SQL port published on Windows. The SQL Server memory setting leaves room below the container limit. fsGroup helps provide access to the mounted volume.

The default StorageClass provisions the 8 GiB PVC named dados-sqlserver-0. The TCP probe checks the port. The Job verifies that it can authenticate and apply the migration.

YAMLk8s/02-sqlserver.yaml
        - name: sqlserver
          image: mcr.microsoft.com/mssql/server:2022-latest
          ports:
            - containerPort: 1433
          env:
            - name: ACCEPT_EULA
              value: "Y"
            - name: MSSQL_PID
              value: "Developer"
            - name: MSSQL_MEMORY_LIMIT_MB
              value: "2048"
            - name: MSSQL_SA_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: banco-secrets
                  key: SA_PASSWORD
          resources:
            requests:
              cpu: "500m"
              memory: "2Gi"
            limits:
              cpu: "2"
              memory: "3Gi"
          volumeMounts:
            - name: dados
              mountPath: /var/opt/mssql
          startupProbe:
            tcpSocket:
              port: 1433
            periodSeconds: 5
            failureThreshold: 60
          readinessProbe:
            tcpSocket:
              port: 1433
            periodSeconds: 5
  volumeClaimTemplates:
    - metadata:
        name: dados
      spec:
        accessModes: ["ReadWriteOnce"]

In k8s/04-api.yaml, change replicas from 1 to 2 in the API Deployment, save, and apply. Confirm that both API Pods are ready and that the Service has both endpoints.

Restore replicas to 1 and reapply at the end. Keeping the change in YAML makes it reproducible. A single port-forward session stays attached to one Pod.

PowerShell
kubectl apply -f .\k8s\04-api.yaml
kubectl -n iac-tutorialk8s rollout status deployment/catalogo-api --timeout=180s
kubectl -n iac-tutorialk8s get pods -l app=catalogo-api
kubectl -n iac-tutorialk8s get endpointslices -l kubernetes.io/service-name=catalogo-api
Experiments

Update and roll back the application

1. Build version 1.1. In CatalogoApi/Program.cs, change the version returned by the root endpoint from 1.0 to 1.1. Save and build from LabIaCK8s.

PowerShell
docker build --platform linux/amd64 --provenance=false `
  -f .\CatalogoApi\Dockerfile -t tutorialk8s-catalogo-api:1.1 .

2. Make the image available. With Rancher Desktop Moby or Docker Desktop Kubeadm, proceed to the YAML after building locally. With Docker Desktop kind, change the image tag in the slide 21 docker image save command from 1.0 to 1.1 and run the updated import block.

3. Edit k8s/04-api.yaml. Find kind: Deployment with metadata.name: catalogo-api. Under spec.template.spec.containers, find name: api. Set image to tutorialk8s-catalogo-api:1.1 and keep imagePullPolicy: IfNotPresent. Preserve indentation and save.

        - name: api
          image: tutorialk8s-catalogo-api:1.1
          imagePullPolicy: IfNotPresent

4. Stop any running port-forward with Ctrl+C, apply the file, and wait for the rollout to complete.

PowerShell
kubectl apply -f .\k8s\04-api.yaml
kubectl -n iac-tutorialk8s rollout status deployment/catalogo-api --timeout=180s
kubectl -n iac-tutorialk8s rollout history deployment/catalogo-api

5. Restart port-forwarding and request http://localhost:8080/ to verify version 1.1. To roll back, restore the 1.0 tag in the manifest and reapply. The database and migration history remain in place.

Troubleshooting

Troubleshoot infrastructure

Pending: inspect Pod events, available resources, and PVC binding. ImagePullBackOff: check the tag, engine, context, and kind import. SQL CrashLoopBackOff: check logs, password, volume permissions, and memory.

PVC Pending: check the default StorageClass and provisioner. Local port occupied: change the host-side port in the forwarding command.

PowerShell
kubectl -n iac-tutorialk8s get pods,pvc,job
kubectl -n iac-tutorialk8s get events --sort-by=.metadata.creationTimestamp
kubectl -n iac-tutorialk8s describe pod sqlserver-0
Troubleshooting

Troubleshoot the application and database

Migration failure: check the Job logs, database DNS, credentials, and migration files in the image. API not Ready: inspect /health/ready and the API logs. Invalid object name Produtos: confirm that the migration Job completed against Catalogo.

If sa login fails on a reused volume, check the password set when that database was initialized. Updating the Secret alone leaves the SQL login password in place. If dotnet ef is unavailable, check the SDK and run dotnet tool restore.

PowerShell
kubectl -n iac-tutorialk8s logs job/db-migrate
kubectl -n iac-tutorialk8s logs deployment/catalogo-api --tail=60
kubectl -n iac-tutorialk8s describe deployment catalogo-api
Wrap-up

Stop workloads or remove the lab

To preserve data, stop port-forwarding and scale both workloads to zero. To resume, reapply the manifests with nonzero replicas and wait for readiness.

PowerShell
kubectl -n iac-tutorialk8s scale deployment/catalogo-api --replicas=0
kubectl -n iac-tutorialk8s scale statefulset/sqlserver --replicas=0
kubectl -n iac-tutorialk8s get pvc

Delete the namespace only when you can discard the lab data. This removes the PVC and can delete its backing storage according to the reclaim policy.

PowerShell
kubectl delete namespace iac-tutorialk8s
